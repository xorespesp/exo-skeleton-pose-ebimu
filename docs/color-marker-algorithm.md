## 1. 풀려는 문제

로봇 다리 관절에 **작은 색 스티커**를 붙였다. 카메라가 옆에서 찍는다.
매 프레임 그 스티커의 **중심이 화면 어디에 있는지** 를 알아내야 한다.

```
        카메라가 본 장면                       원하는 결과
   +---------------------------+        +---------------------------+
   |                           |        |                           |
   |        [] <- 골반          |        |        + (612.3, 240.7)   |
   |         \                 |        |         \                 |
   |          [] <- 무릎        |   ->   |          + (598.1, 512.4)  |
   |          |                |        |          |                |
   |          [] <- 발목        |        |          + (601.8, 780.2)  |
   |         /                 |        |         /                 |
   |       []  <- 발            |        |       +  (640.5, 845.9)   |
   +---------------------------+        +---------------------------+
```

중심을 알면 그 점들로 뼈의 방향을 구할 수 있고, 방향의 변화가 곧 관절 각도가 된다.
**이 문서는 "점을 찾는 것" 까지만 다룬다.**

중요한 조건이 두 개 있다.

- **정확해야 한다.** 중심이 1픽셀 흔들리면 각도가 흔들린다.
- **작아야 한다.** 마커가 크면 관절 위치를 가리고 로봇 동작을 방해한다.

## 3. 준비: 영상은 숫자 덩어리다

### 픽셀과 채널

디지털 사진은 작은 사각형(**픽셀**)이 격자로 늘어선 것이다. 컬러 사진은 픽셀마다 숫자 세 개를
갖는다. 각각 파랑, 초록, 빨강의 세기이며 0~255 범위다. 이 세 개를 **채널** 이라 부른다.

```
   화면의 일부를 확대하면

   +-----+-----+-----+
   | 픽셀 | 픽셀 | 픽셀 |          픽셀 하나 = (B, G, R)
   +-----+-----+-----+          예) (126, 0, 230)  <- 마젠타
   | 픽셀 | 픽셀 | 픽셀 |               (100, 98, 96) <- 회색 배경
   +-----+-----+-----+
```

OpenCV 는 순서가 **B, G, R** 이다. 흔히 쓰는 RGB 와 반대라 처음에 헷갈리기 쉽다.

2448 x 2048 컬러 프레임 하나는 픽셀이 약 500만 개, 숫자가 1500만 개다.
**이 숫자들을 픽셀마다 어떻게 빨리 처리하느냐** 가 알고리즘 설계의 큰 부분을 차지한다.

## 4. 1단계: 색을 다루기 좋은 형태로 바꾸기

### RGB 로 색을 판정하면 생기는 문제

마커가 마젠타라고 하자. 밝은 곳에서는 `(126, 0, 230)`, 그늘에서는 `(63, 0, 115)` 로 찍힌다.
**같은 색인데 숫자가 전부 절반이 됐다.**

```
   밝은 곳         그늘
   B 126          B  63
   G   0    ->    G   0      숫자가 전부 반으로
   R 230          R 115
```

RGB 세 숫자를 그대로 비교하면 이 둘을 다른 색으로 본다. 그림자만 져도 마커를 놓친다는 뜻이다.

### 해법: 밝기를 따로 떼어내기

**CIE Lab** 이라는 표현 방식은 색을 다른 세 축으로 나눈다.

```
   L*  밝기          어두움 0 <---------> 100 밝음
   a*  초록 <-> 빨강   초록 -128 <---- 0 ----> +127 빨강
   b*  파랑 <-> 노랑   파랑 -128 <---- 0 ----> +127 노랑
```

핵심은 **밝기가 L* 하나에 몰려 있다는 것** 이다. 그늘이 지면 L* 만 내려가고 a*, b* 는 거의
그대로다.

```
   밝은 곳                그늘
   L*  50                L*  28      <- 이것만 바뀜
   a* +79                a* +78      <- 거의 그대로
   b*  -3                b*  -4      <- 거의 그대로
```

그래서 이 알고리즘은 **L* 를 아예 버리고 (a*, b*) 두 개만 쓴다.**
그림자, 노출 변화, 조명 밝기 변동을 한 번에 무시하게 된다.

### (a\*, b\*) 평면

두 숫자만 남으니 색 하나가 평면 위의 점 하나가 된다. 이 평면이 앞으로 계속 나온다.

```
              b* (노랑)
               ^
          +100 |
               |         o 주황
           +50 |
               |
             0 +--------------o------> a* (빨강)
               |  0     +50   +100
           -50 |              o 마젠타
               |
   o 시안 -100 |
               |
             (파랑)
```

코드에서는 한 줄이다.

```cpp
cv::cvtColor(bgr, _lab, cv::COLOR_BGR2Lab);
```

> **알아둘 점.** OpenCV 가 8비트 영상에서 a*, b* 를 저장할 때 음수를 담을 수 없어서 128 을
> 더해 놓는다. 저장값 200 은 실제로는 `200 - 128 = +72` 다. 코드에 나오는 `kLabShift = 128.0`
> 이 이것이다.

## 5. 2단계: 색 모델 만들기

### 왜 미리 정해 둘 수 없나

"마젠타는 a\*+79, b\*-3" 이라고 코드에 박아 두면 안 된다. 시험소마다 조명이 다르고 카메라
설정이 다르고 인쇄한 잉크가 다르다. 같은 스티커가 여기서는 a\*+79, 저기서는 a\*+68 로 찍힌다.

그래서 **현장에서 실제로 찍은 픽셀을 모아 기준을 만든다.**

### 표본 모으기

사용자가 화면에서 마커를 클릭하면, 커서 주변 원 안의 픽셀들이 표본으로 쌓인다.

```
   화면에서 마커를 클릭                 모인 픽셀들을 (a*, b*) 평면에 찍으면
   +-------------+
   |             |                          b*
   |    ####     |                           |
   |   ######    |                        0  |      ..:::..
   |   ###O##    | <- 클릭                    |    .:::::::::.     <- 구름처럼 뭉친다
   |   ######    |                       -5  |     ':::::::'
   |    ####     |                           |       ':::'
   |             |                           +---+---+---+---+-> a*
   +-------------+                              70  75  80  85
```

한 점이 아니라 **구름** 이 되는 이유는 여러 가지다. 센서 노이즈, 마커 표면의 미세한 밝기 차,
Bayer 보간(뒤에서 설명), 인쇄 얼룩 등.

이 구름의 **모양과 위치가 곧 색 모델이다.**

### 무엇을 저장하는가

구름을 요약하는 숫자는 다섯 개면 충분하다.

```
   평균     ā  = a* 들의 평균         구름의 중심이 어디인가
            b̄  = b* 들의 평균

   퍼짐     σa² = a* 방향으로 퍼진 정도    구름이 얼마나 넓은가
            σb² = b* 방향으로 퍼진 정도
            σab = a* 와 b* 가 같이 움직이는 정도  (구름이 기울었는가)
```

마지막 `σab` 를 **공분산** 이라 한다. 이것이 0 이면 구름이 축과 나란하고, 0 이 아니면
비스듬히 기울어 있다는 뜻이다.

```
   σab = 0 (안 기울음)          σab > 0 (기울음)

        b*                          b*
         |    .:::.                  |        .::.
         |  .:::::::.                |      .::::.
         |   ':::::'                 |    .::::.
         +----------> a*             |  .::.
                                     +----------> a*
```

### 픽셀을 다 들고 있지 않는다

수천, 수만 개 픽셀을 배열에 쌓을 필요가 없다. 평균과 퍼짐은 **합만 있으면** 계산된다.

```
   픽셀이 들어올 때마다 여섯 개 숫자만 갱신

   개수 n      += 1
   Σa          += a
   Σb          += b
   Σa²         += a * a
   Σab         += a * b
   Σb²         += b * b
```

나중에 이렇게 꺼낸다.

```
   ā   = Σa / n
   σa² = (Σa² - n·ā²) / (n-1)
   σab = (Σab - n·ā·b̄) / (n-1)
```

코드에서는 `color_sampler::add()` 가 합을 쌓고 `color_sampler::fit()` 이 꺼낸다.

> **왜 `n` 이 아니라 `n-1` 로 나누나.** 표본에서 계산한 평균을 다시 쓰기 때문에 퍼짐이 실제보다
> 조금 작게 나온다. `n-1` 로 나누면 그 치우침이 보정된다. 표본이 많으면 차이는 미미하다.

### 표본은 여러 자세에서 모아야 한다

한 자세에서만 찍으면 구름이 아주 좁게 나온다. 그러면 마커가 조금만 다른 빛을 받아도 구름 밖으로
나가서 놓친다.

```
   한 자세에서만 표본 수집        여러 자세에서 표본 수집

        b*                            b*
         |                             |
         |    .:.                      |    .:::::.
         |    ':'                      |  .:::::::::.
         |                             |    ':::::'
         +---------> a*                +-----------> a*
      좁다 -> 조금만 변해도 놓침     넓다 -> 변동을 견딤
```

GUI 의 `spread` 표시가 이 폭이다. **표본을 더 모아도 spread 가 안 커질 때까지** 찍는 것이 요령이다.

## 6. 3단계: 얼마나 닮았는지 재기

이제 새 픽셀 하나가 들어왔다. 이게 구름에 속하는지 어떻게 판정할까.

### 방법 1: 상자로 자르기

"a* 는 72~86, b* 는 -8~+2 사이면 통과."

```
        b*
         |  +-------------+
       0 |  |    ..:::..  |
         |  |  .:::::::::.|
      -5 |  |   ':::::::' |
         |  +-------------+
         +-------------------> a*
              ^          ^
        모서리에 점이 없는데도 통과시킨다
```

구름이 기울어 있으면 상자 모서리로 **배경이 들어온다.** 상자를 줄이면 이번엔 구름 끝이 잘린다.
흔히 쓰는 HSV 임계값 방식이 이 문제를 갖는다.

### 방법 2: 자로 재기 (유클리드 거리)

"중심에서 거리 R 이내면 통과." 즉 원이다.

```
        b*
         |     .-''-.
       0 |   /..:::..\
         |  |.:::::::::|
      -5 |   \':::::::/
         |     '-..-'
         +-------------------> a*

   구름이 옆으로 길면 원으로는 못 맞춘다
   키우면 위아래로 배경이 들어오고
   줄이면 좌우로 마커가 잘린다
```

### 방법 3: 마할라노비스 거리

**각 방향의 편차를 그 방향의 퍼짐으로 나눈다.**

구름이 기울지 않았다면 식이 이렇게 단순하다.

```
   d² = ( (a - ā) / σa )²  +  ( (b - b̄) / σb )²
```

`(a - ā)` 는 "평균에서 얼마나 떨어졌나" 이고, 이걸 `σa` 로 나누면 **"몇 배만큼 떨어졌나"** 가
된다. 그래서 결과에 단위가 없고, 어느 축이든 같은 잣대로 비교된다.

구름이 기울었으면 축별로 나누는 것만으로 부족한데, 공분산의 역행렬이 그 기울기까지 처리한다.
그것을 행렬로 쓴 것이 아래 식이다.

```
   d² = (p - 평균)ᵀ · 공분산⁻¹ · (p - 평균)
```

기하학적 의미가 핵심이다. **같은 거리인 점들을 이으면 원이 아니라, 구름과 같은 모양 같은 방향의
타원이 된다.**

```
        b*
         |      .-'''''''-.           d = 3
         |    .'  .-''''-.  '.
       0 |   /   /  ..:::..  \  \     d = 2
         |  |   |  .:::::::::. |  |
      -5 |   \   \  ':::::::' /  /    d = 1
         |    '.  '-......-'  .'
         |      '-.........-'
         +-------------------------> a*
```

"타원을 원으로 펴서 잰 거리" 라고 이해하면 된다. 퍼진 방향으로는 멀어도 관대하고, 좁은
방향으로는 조금만 벗어나도 멀다고 본다.

### 기준값 하나

판정은 `d < max_distance` 하나로 끝난다. HSV 상자는 여섯 개(H/S/V 최소·최대)를 맞춰야 하지만
여기서는 **사람이 정할 값이 하나뿐이다.**

게다가 그 값이 명확한 뜻을 갖는다. 2차원 정규분포에서 `d < k` 일 확률은 `1 - exp(-k²/2)` 다.

```
   max_distance = 2.0  ->  표본의 약 86.5% 를 덮는다
   max_distance = 3.0  ->  약 98.9%
```

## 7. 4단계: 미리 계산해 두기

### 문제: 500만 번 계산

매 프레임 픽셀마다 마할라노비스 거리를 구하면 곱셈과 제곱근이 500만 번씩 돈다.
초당 79프레임이면 이것만으로 예산을 다 쓴다.

### 해법: 답을 미리 적어 둔 표

여기서 결정적인 사실이 하나 있다. **가능한 (a, b) 조합이 유한하다.**

8비트 영상에서 a 와 b 는 각각 0~255 정수다. 조합은 `256 x 256 = 65536` 가지뿐이다.

```
   65536 가지밖에 없다면, 전부 미리 계산해서 표로 만들어 두면 된다.

        b=0   b=1   b=2  ...  b=255
   a=0 [  0 ][  0 ][  0 ] ... [  0 ]
   a=1 [  0 ][  0 ][  0 ] ... [  0 ]
   ...
  a=200[  0 ][ 12 ][ 48 ] ... [  0 ]     <- 마커 색 근처만 0 이 아니다
  a=201[  5 ][ 90 ][188 ] ... [  0 ]
  a=202[ 20 ][170 ][255 ] ... [  0 ]     <- 255 = 모델 정중앙
   ...
```

표 크기는 65536 바이트, 즉 **64 KB** 다. CPU 캐시에 들어가는 크기라 조회가 매우 빠르다.

이제 픽셀 하나를 처리하는 데 드는 일이 **표 조회 한 번** 이다.

```cpp
dst[x] = _lut[src[x][1] * 256 + src[x][2]];
//              ^ a 값        ^ b 값
```

HSV 임계값 방식이 픽셀당 비교 6번을 하는 것보다 **오히려 빠르다.**
"제대로 된 방법이 간단한 방법보다 느리다" 는 통념이 여기서는 뒤집힌다.

### 표에 무엇을 적는가

0 아니면 255 만 적을 수도 있지만, 그러면 정보가 아깝다. 대신 **중심에서 1, 경계에서 0 으로
부드럽게 떨어지는 점수** 를 적는다.

```
   w = 1 - (거리 / max_distance)          w 가 0 이하면 0

   거리 0.0  ->  점수 255   (모델 정중앙)
   거리 1.5  ->  점수 128   (딱 절반)
   거리 3.0  ->  점수   0   (경계)
   거리 4.0  ->  점수   0   (밖)
```

이 점수 하나가 두 가지 역할을 한다.

```
   점수 > 0        ->  마스크 (마커 색인가 아닌가)
   점수의 크기      ->  9단계 무게중심의 가중치
```

표는 색 모델이 바뀔 때만 다시 만든다. 코드에서는 `rebuild_lut()` 이다.

## 8. 5단계: 점수 영상과 마스크

이제 매 프레임 하는 일이다.

```
   [Lab 영상]              [점수 영상]                [마스크]

   픽셀마다 (L,a,b)   ->   픽셀마다 0~255      ->     픽셀마다 0 또는 255
   표 조회                                          점수 > 0 이면 255
```

숫자로 보면 이렇다.

```
   점수 영상 (마커 주변 확대)           마스크

     0   0   0  30   0   0             .   .   .   #   .   .
     0   0  95 210  88   0             .   .   #   #   #   .
     0  92 240 255 235  85      ->     .   #   #   #   #   #
    28 205 250 252 208  25             #   #   #   #   #   #
     0  85 225 230  90   0             .   #   #   #   #   .
     0   0  25   0   0   0             .   .   #   .   .   .
```

마스크는 **모양 정보만 남고 얼마나 확실한지는 사라진** 상태다. 그래서 점수 영상을 버리지 않고
9단계까지 들고 간다.

코드에서는 `_build_score_image()` 와 `cv::threshold()` 다.

## 9. 6단계: 마스크 다듬기

마스크에는 두 가지 흠이 있다.

```
   흠 1. 배경에 흩어진 작은 점들          흠 2. 마커 안의 구멍

   . . . . . . . .                      . . . . . . .
   . # # # # . . .                      . # # # # # .
   . # # # # . . .                      . # # . . # .   <- 광택 하이라이트로
   . # # # # . . .                      . # # . . # .      가운데가 하얗게 날아감
   . # # # # . . .                      . # # # # # .
   . . . . . . # .   <- 노이즈           . . . . . . .
   . . . . . . . .
```

이걸 고치는 도구가 **형태 연산** 이다. 기본 동작 두 개로 만들어진다.

### 침식 (erosion)

작은 도장(**커널**)을 픽셀마다 대 보고, **도장이 흰 영역 안에 완전히 들어갈 때만** 그 픽셀을
남긴다. 결과적으로 흰 영역이 테두리부터 깎인다.

```
   3x3 도장을 쓸 때

   원본                      침식 후
   . . . . . . . .           . . . . . . . .
   . # # # # . . .           . . . . . . . .
   . # # # # . . .           . . # # . . . .    <- 테두리 한 겹이 깎임
   . # # # # . . .           . . # # . . . .
   . # # # # . . .           . . . . . . . .
   . . . . . . # .           . . . . . . . .    <- 점 노이즈는 사라짐
   . . . . . . . .           . . . . . . . .
```

**점 노이즈는 도장보다 작아서 통째로 사라진다.** 이게 핵심이다.

### 팽창 (dilation)

반대다. 도장이 흰 영역에 **하나라도 걸치면** 그 픽셀을 켠다. 흰 영역이 테두리 밖으로 부푼다.

```
   침식 결과                 팽창 후
   . . . . . . . .           . . . . . . . .
   . . . . . . . .           . # # # # . . .
   . . # # . . . .           . # # # # . . .    <- 원래 크기로 복귀
   . . # # . . . .           . # # # # . . .
   . . . . . . . .           . # # # # . . .
   . . . . . . . .           . . . . . . . .    <- 사라진 노이즈는 안 돌아옴
   . . . . . . . .           . . . . . . . .
```

### 열림 = 침식 -> 팽창

두 개를 이 순서로 하면 **작은 점만 지우고 큰 덩어리는 원래 크기로 되돌아온다.**

```
   원본           침식          팽창 (= 열림 결과)
   ####  .        . .           ####
  ###### .   ->   ##      ->   ######
   ####           . .           ####
   (노이즈 있음)   (노이즈 소멸)   (노이즈 없이 복원)
```

파라미터가 `open_kernel_px` 다. 도장 크기이며, **이보다 작은 점은 사라진다.**

### 닫힘 = 팽창 -> 침식

순서를 바꾸면 목적이 정반대가 된다. **구멍을 메운다.**

```
   원본            팽창             침식 (= 닫힘 결과)
   . . . . . . .   . . . . . . .    . . . . . . .
   . # # # # # .   # # # # # # #    . # # # # # .
   . # # . . # .   # # # # # # #    . # # # # # .   <- 구멍이 메워짐
   . # # . . # .   # # # # # # #    . # # # # # .
   . # # # # # .   # # # # # # #    . # # # # # .
   . . . . . . .   # # # # # # #    . . . . . . .   <- 크기는 원래대로
```

팽창 단계에서 구멍이 안쪽에서 메워지고, 침식 단계에서 바깥 테두리만 다시 깎인다.
**한 번 메워진 구멍은 돌아오지 않는다.**

파라미터가 `close_kernel_px` 다.

### 왜 구멍이 생기고, 왜 문제인가

마커 표면이 광택이면 조명이 반사되어 한가운데가 하얗게 날아간다. 그 픽셀은 색 정보를 잃어서
마스크에서 빠진다. 결과는 도넛 모양이다.

문제는 **하이라이트가 다리 움직임을 따라 이동한다는 것** 이다. 도넛의 구멍이 왼쪽에 있다가
오른쪽으로 옮겨가면, 무게중심도 따라 흔들린다. 마커는 가만히 있는데 측정값이 움직인다.

```
   하이라이트 왼쪽          하이라이트 오른쪽
    ##  ####                ####  ##
   ### ,#####              #####, ###
    ##  ####                ####  ##
      ^ 중심이 오른쪽         ^ 중심이 왼쪽
```

닫힘으로 메우면 이 흔들림이 사라진다. **근본 해결은 무광 마커를 쓰는 것** 이고, 닫힘은 보험이다.

## 10. 7단계: 덩어리로 묶기

마스크는 아직 흰 픽셀의 집합일 뿐이다. **어디부터 어디까지가 하나의 물체인지** 를 정해야 한다.

규칙은 단순하다. **서로 닿아 있는 흰 픽셀은 같은 덩어리다.**

```
   마스크                        라벨 (덩어리마다 번호)

   . # # . . # .                 . 1 1 . . 2 .
   . # # . . # .                 . 1 1 . . 2 .
   . . . . . . .        ->       . . . . . . .
   . . # # # . .                 . . 3 3 3 . .
   . . # # # . .                 . . 3 3 3 . .
```

이 작업을 **연결 요소 라벨링** 이라 하고, OpenCV 함수 하나로 끝난다.

```cpp
cv::connectedComponentsWithStats(_mask, _labels, _stats, _centroids, 8, CV_32S);
```

`8` 은 대각선으로 닿은 것도 같은 덩어리로 본다는 뜻이다. `4` 로 하면 상하좌우만 인정한다.

이 함수는 덩어리마다 **면적** 과 **감싸는 사각형** 을 덤으로 준다. 다음 단계가 그걸 쓴다.

---

## 11. 8단계: 크기와 모양으로 거르기

### 왜 필요한가

색만 맞으면 배경도 걸린다. 붉은 공구함, 누군가의 옷, 벽에 붙은 안내판.

```
   덩어리 후보들
   +--------------------------------+
   |   ###                          |
   |  #####  <- 마커                 |
   |   ###          ############    |
   |                ############    | <- 벽에 붙은 큰 안내판
   |      .         ############    |
   |      ^ 점 노이즈                 |
   +--------------------------------+
```

**크기와 모양** 으로 마커만 남긴다. 네 가지를 본다.

### 감싸는 사각형

먼저 용어 하나. **감싸는 사각형(외접 사각형)** 은 덩어리를 둘러싸는 가장 작은 직사각형이다.
7단계에서 이미 받아 놨다.

```
   +---------+  <- 감싸는 사각형
   | ####### |
   |#########|     가로 20, 세로 20
   |#########|
   | ####### |
   +---------+
```

> **"원을 찾는 알고리즘인데 왜 사각형?"**
> 원을 직접 찾는 것이 아니다. 색이 맞는 덩어리를 먼저 찾고, **그것이 원처럼 생겼는지를 사각형으로
> 검사한다.** 원이라면 두 가지가 성립하기 때문이다.
> - 가로와 세로가 같다
> - 그 사각형의 78.5% 를 채운다 (원의 넓이 / 정사각형 넓이 = pi/4)

### 검사 1, 2: 면적 (얼마나 큰가)

덩어리에 속한 픽셀 개수다. 너무 작으면 노이즈, 너무 크면 배경이다.

```
   지름 d 원의 넓이 = pi · d² / 4

   지름 10 px  ->   79 px²
   지름 20 px  ->  314 px²      <- 우리 마커
   지름 40 px  -> 1257 px²
```

파라미터는 `min_area_px`, `max_area_px` 다.

### 검사 3: 채움율 (얼마나 꽉 찼나)

```
   채움율 = 덩어리 면적 / 감싸는 사각형 면적
```

**면적이 같아도 모양은 다를 수 있다.** 채움율이 그 차이를 잡는다.

```
   원반 (정상)                     도넛 (구멍이 남음)
   +---------+                     +---------------+
   | ####### |                     |   ########    |
   |#########|                     |  ##      ##   |
   |#########|                     |  ##      ##   |
   | ####### |                     |   ########    |
   +---------+                     +---------------+
   면적    314                      면적    314   <- 같다!
   사각형  400                      사각형  900
   채움율  0.785                    채움율  0.35  <- 여기서 갈린다
```

파라미터는 `min_fill` 이다. 기본 0.55 로, 원의 0.785 보다 여유를 뒀다.

### 검사 4: 종횡비 (얼마나 길쭉한가)

```
   종횡비 = 사각형의 긴 변 / 짧은 변       원이면 1.0
```

```
   원                줄무늬 (모션 블러)
   +------+          +------------------+
   |######|          |##################|
   |######|          |##################|
   +------+          +------------------+
   20 / 20 = 1.0     48 / 20 = 2.4
```

노출 시간이 길면 스윙하는 마커가 줄무늬로 늘어난다. **이 값은 노출을 충분히 줄이기 전까지
넉넉하게 잡아야 한다.**

```
   지름 20 px, 화면상 속도 3478 px/s 기준
   노출 1 ms  ->  24 x 20  ->  1.2
   노출 2 ms  ->  27 x 20  ->  1.35
   노출 8 ms  ->  48 x 20  ->  2.4
```

파라미터는 `max_aspect` 다.

### 네 검사를 합치면

```
   도형        종횡비   채움율     판정
   ---------------------------------------------
   원반         1.0     0.785     통과
   정사각형     1.0     1.00      탈락 (너무 꽉 참)
   도넛         1.0     0.35      탈락 (덜 참)
   줄무늬       2.4     0.78      탈락 (길쭉함)
   점 노이즈    1.0     0.80      탈락 (면적 미달)
```

### 왜 교과서 공식을 안 쓰나

원형도를 재는 표준 공식이 있다.

```
   원형도 = 4 · pi · 면적 / 둘레²        원이면 1.0
```

그런데 **작은 덩어리에서는 둘레 추정이 부정확하다.** 픽셀이 계단 모양이라 실제보다 둘레가
길게 나오고, 그러면 원형도가 실제보다 낮게 계산된다.

```
   진짜 원의 둘레            픽셀로 그린 원의 둘레
      .-''-.                   ,--,
    /        \                _|  |_
   |          |              |      |
    \        /               |_    _|
      '-..-'                   '--'
   매끄러움                  계단이라 더 길다
```

지름 20 px 수준에서는 이 오차가 크다. 그래서 채움율과 종횡비를 쓴다.

### 탈락 사유를 세어 둔다

거를 때마다 이유별로 개수를 기록한다.

```cpp
if (area < min_area)   { ++_rejects.too_small;  continue; }
if (area > max_area)   { ++_rejects.too_large;  continue; }
if (fill < min_fill)   { ++_rejects.not_filled; continue; }
if (aspect > max_asp)  { ++_rejects.too_long;   continue; }
```

**마커가 안 잡힐 때 어느 값을 고쳐야 하는지 즉답해 주기 위해서다.** GUI 에 그대로 표시된다.

## 12. 9단계: 중심을 정밀하게 찾기

살아남은 덩어리마다 중심을 구한다. 여기가 알고리즘의 최종 산출물이다.

### 단순히 세면 부정확하다

흰 픽셀의 좌표를 평균 내는 방법(**이진 무게중심**)을 먼저 보자.

```
   1차원으로 단순화한 예

   픽셀 번호:    0    1    2    3    4
   점수:         0   60  255  200   10
   마스크:       .    #    #    #    #

   이진 무게중심 = (1 + 2 + 3 + 4) / 4 = 2.50
```

문제는 **4번 픽셀이다.** 점수가 10 밖에 안 되는 거의 배경인 픽셀인데, 1번(점수 60)과 똑같이
한 표를 행사한다. 그래서 중심이 오른쪽으로 끌려간다.

더 큰 문제는 **계단처럼 튄다는 것** 이다. 마커가 0.1 px 움직여서 4번 픽셀이 꺼지면 중심이
갑자기 0.25 px 점프한다.

### 점수를 가중치로 쓴다

```
   가중 무게중심 = Σ(점수 × 좌표) / Σ(점수)

   = (60×1 + 255×2 + 200×3 + 10×4) / (60 + 255 + 200 + 10)
   = (60 + 510 + 600 + 40) / 525
   = 1210 / 525
   = 2.30
```

경계 픽셀이 **자기 확신만큼만 표를 행사한다.** 4번은 10/525 = 2% 만 기여한다.

```
   기여도 비교

   픽셀   이진      가중
   1      25%       11%
   2      25%       49%     <- 확실한 픽셀이 크게 기여
   3      25%       38%
   4      25%        2%     <- 애매한 픽셀은 거의 무시
```

### 왜 이게 결정적인가

마커가 아주 조금 움직였을 때의 반응이 다르다.

```
   마커가 오른쪽으로 0.1 px 이동

   이진 무게중심:  픽셀이 켜지거나 꺼지는 순간에만 변한다  ->  계단
   가중 무게중심:  경계 픽셀의 점수가 조금씩 변한다        ->  매끄러움


   측정된 중심
      ^                        ^
      |    _|                  |      /
      |  _|      계단식        |    /      매끄러움
      |_|                      |  /
      +--------> 실제 위치      +--------> 실제 위치
```

각도를 재려면 중심이 **매끄럽게** 움직여야 한다. 계단식이면 각도도 계단식으로 튄다.

합성 영상 실험에서 이 방식의 오차가 **0.025 px** 로 측정됐다 (`--color-selftest`).

### 구현

덩어리의 감싸는 사각형 안만 돌면 되므로 빠르다.

```cpp
for (사각형 안의 픽셀 (x, y))
{
    if (라벨[y][x] != 이 덩어리 번호) continue;  // 옆 덩어리가 끼어 있을 수 있다

    w = 점수[y][x];
    합계  += w;
    합계x += w * x;
    합계y += w * y;
}
중심 = (합계x / 합계, 합계y / 합계);
```

## 13. 파라미터 지도

어떤 값이 어느 단계에서 작동하는지 한눈에 본다.

```
   단계                        파라미터                 GUI 위치
   ------------------------------------------------------------------
   2. 색 모델 만들기            (클릭으로 표본 수집)      Sample radius
   3. 닮음 판정                max_distance            Max distance
   6. 마스크 다듬기             open_kernel_px          open kernel
                              close_kernel_px         close kernel
   8. 크기/모양 거르기          min_area_px             min area
                              max_area_px             max area
                              min_fill                min fill
                              max_aspect              max aspect
```

각 값을 올리고 내렸을 때의 방향은 이렇다.

| 파라미터 | 올리면 | 내리면 |
|---|---|---|
| `Sample radius` | 표본이 빨리 쌓임, 테두리를 물 위험 | 안전하지만 클릭을 더 해야 함 |
| `max_distance` | 마커 테두리까지 포함, 배경이 샘 | 마커 중심부만, 덩어리가 작아짐 |
| `open_kernel_px` | 마스크가 깨끗해짐, 얇은 테두리 깎임 | 노이즈가 남음 |
| `close_kernel_px` | 큰 구멍도 메움, 이웃 덩어리와 합쳐짐 | 구멍이 남아 채움율이 낮아짐 |
| `min_area_px` | 노이즈 제거, 먼 마커도 탈락 | 작은 것도 통과 |
| `max_area_px` | 큰 배경도 통과 | 큰 배경 차단 |
| `min_fill` | 꽉 찬 것만, 구멍 뚫린 마커 탈락 | 찌그러진 배경도 통과 |
| `max_aspect` | 블러를 견딤, 길쭉한 배경도 통과 | 동그란 것만 |

## 14. 안 될 때 어디를 보나

파이프라인 순서대로 좁혀 나가면 원인이 금방 잡힌다.

### 순서대로 확인하기

```
   1. 화면에 마커가 보이나?                    -> 안 보이면 카메라/조명 문제
   2. Backdrop 을 Score 로 놓았을 때
      마커 자리가 밝게 나오나?                 -> 아니면 색 모델 문제 (3단계)
   3. Backdrop 을 Mask 로 놓았을 때
      마커가 덩어리로 보이나?                  -> 아니면 형태 연산 문제 (6단계)
   4. rejected 카운터에 숫자가 찍히나?          -> 찍히면 필터 문제 (8단계)
   5. 표의 x, y 소수점이 .00 만 나오나?         -> 그러면 가중 무게중심 문제 (9단계)
```

### 증상별 대처

| 증상 | 원인 단계 | 대처 |
|---|---|---|
| Score 가 전부 캄캄함 | 3 | 색 모델이 안 맞음. 다시 샘플링하거나 `max_distance` 를 올린다 |
| Score 는 밝은데 Mask 가 비었음 | 5 | 있을 수 없다. 점수 > 0 이면 마스크에 남는다 |
| 마스크가 점투성이 | 6 | `open_kernel_px` 를 올린다 |
| 마커 가운데가 뚫림 | 6 | `close_kernel_px` 를 올린다. 근본은 무광 마커 |
| rejected: small 이 큼 | 8 | `min_area_px` 를 내리거나 마커를 키운다 |
| rejected: large 가 큼 | 8 | `max_area_px` 를 내린다. 배경이 색에 걸린 것 |
| rejected: unfilled 가 큼 | 8 | `close_kernel_px` 를 올린다. 그래도 안 되면 `min_fill` 을 내린다 |
| rejected: elongated 가 큼 | 8 | 노출을 줄인다. 임시로 `max_aspect` 를 올린다 |
| 전부 0 인데 마커도 0 | 3 | 색 모델 문제. Score 를 보고 `max_distance` 를 올린다 |
| 중심이 정수로만 나옴 | 9 | `max_distance` 가 너무 좁아 모든 픽셀이 같은 가중치를 받는 상태 |
| 중심이 프레임마다 떨림 | 6, 9 | 광택 하이라이트를 의심. `close_kernel_px` 와 마커 재질 확인 |

### 자주 겪는 함정

**자동 노출 / 자동 화이트밸런스가 켜져 있음.**
다리가 스윙할 때마다 화면 전체 톤이 변해서 어떤 색 모델도 무너진다. GUI 의 Exposure/Gain
패널에서 `ExposureAuto`, `GainAuto`, `BalanceWhiteAuto` 가 모두 Off 인지 확인한다.

**한 자세에서만 표본을 뽑음.**
`spread` 가 1~2 수준으로 작으면 이 상태다. 다리를 여러 자세로 옮겨 가며 더 찍는다.

**노출이 너무 김.**
기본 8000 µs 는 색 마커 추적에 길다. 마커가 줄무늬로 늘어나 종횡비 필터에 걸리고, 번짐 때문에
가장자리 색이 흐려져 마스크 면적도 줄어든다. 1000~2000 µs 를 목표로 하고 광량은 조명으로
벌충한다.

**광택 용지에 인쇄함.**
정반사 하이라이트가 마커 가운데를 하얗게 날려서 도넛을 만든다. 무광 용지를 쓴다.

## 부록: Bayer 센서 이야기

VZ 카메라는 픽셀마다 색 세 개를 직접 측정하지 않는다. **센서 위에 색 필터가 격자로 깔려 있어
픽셀마다 한 가지 색만 잰다.**

```
   센서 위의 필터 배열 (Bayer 패턴)

   R  G  R  G      R 을 재는 픽셀: 전체의 25%
   G  B  G  B      G 를 재는 픽셀: 전체의 50%
   R  G  R  G      B 를 재는 픽셀: 전체의 25%
   G  B  G  B
```

나머지 두 색은 **이웃에서 추정한다.** 이 과정을 디모자이크라 한다.

여기서 나오는 결과가 두 가지다.

**색 해상도가 밝기의 절반이다.** 지름 20 px 마커라면 실제로 R 을 측정한 픽셀은 100개 남짓이다.
그래서 마커 지름을 15~20 px 아래로 내리지 않는 것이 좋다.

**가장자리에 색 번짐이 생긴다.** 이웃에서 추정하다 보니 마커와 배경의 경계에서 없던 색이
만들어진다. 다행히 9단계의 가중 무게중심이 이런 픽셀에 낮은 가중치를 주므로 중심 오차로는
크게 이어지지 않는다.

## 정리

```
   무엇을 했나                            핵심 아이디어
   -------------------------------------------------------------------
   1. 색공간 변환                         밝기를 버리면 그림자에 강해진다
   2. 표본에서 색 모델 만들기              값을 박아 두지 않고 현장에서 배운다
   3. 마할라노비스 거리                    구름 모양에 맞춰 거리를 잰다
   4. 룩업 테이블                         답이 65536가지뿐이니 미리 계산한다
   5. 점수 영상                           마스크와 가중치를 한 값으로 겸한다
   6. 형태 연산                           점을 지우고 구멍을 메운다
   7. 연결 요소                           붙은 것끼리 물체로 묶는다
   8. 크기/모양 필터                       원처럼 생긴 것만 남긴다
   9. 가중 무게중심                        경계 픽셀이 확신만큼만 표를 행사한다
```

지금 구현은 **색 클래스 하나** 만 다룬다. 마커 네 개를 서로 구분하는 문제(어느 것이 무릎이고
어느 것이 발목인가)는 아직 없다. 그 부분은 `color-marker-detection.md` 의 5절에 설계가 있고,
색을 두 가지로 번갈아 붙이고 세로 순서와 이전 프레임 위치로 배정하는 방식이다.
