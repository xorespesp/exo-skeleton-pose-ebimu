# 색상 마커 검출 모드 설계 (sagittal 전용)

sagittal 뷰에서 AprilTag 대신 **단색 마커**로 하지 관절을 검출하는 모드의 설계안이다.
아직 구현 전이며, 이 문서는 무엇을 만들지와 왜 그렇게 만드는지를 정리한다.

대상 카메라는 Vieworks VZ-5MU-C79H00 (`Vieworks-VZ-5MU-C79H00-spec.md`), 운용 환경은
시험소 내부 실험실이다. **조명과 배경을 어느 정도 통제할 수 있다**는 것이 이 설계의 전제이자
가장 큰 자산이다.

---

## 1. 요구사항

- 마커가 작아야 한다 (AprilTag 50 mm 대비 확실히 작게)
- 관절 위치 추정 정확도가 좋아야 한다
- 시험소마다 조명·배경이 달라도 현장에서 맞출 수 있어야 한다
- sagittal 뷰 한정. frontal 확장은 지금 목표가 아니다

---

## 2. 난이도 요약

색 임계화 자체는 쉽다. 실제로 어려운 지점은 따로 있다.

| 항목 | 난이도 | 비고 |
|---|---|---|
| 색 분류 | 낮음 | 샘플링 + 마할라노비스로 40줄 남짓. 축정렬 임계화보다 오히려 빠르다 |
| **마커 identity 부여** | **높음** | 태그와 달리 블롭은 "어느 관절인지"를 안 알려줌 |
| **시험소별 튜닝 워크플로** | **높음** | 사람이 슬라이더로 맞추게 하면 현장에서 실패 |
| 조명 변동 대응 | 중간 | 카메라 고정 + 기준 패치로 대부분 해결 |
| 모션 블러 | 중간 | 노출을 줄이면 해결. 조명 통제가 레버 |

집중 작업 기준 **1.5 ~ 2주** 규모로 본다.

### 정확도는 오히려 유리하다

AprilTag은 비트 격자를 해상해야 디코딩된다. `tagStandard41h12`는 셀당 최소 4 ~ 6 px이 필요해
실질 하한이 30 ~ 40 px이다. 단색 원형 블롭은 지름 10 px에서도 안정적으로 잡히고,
15 ~ 25 px이면 centroid 표준편차가 0.1 px 아래로 내려간다.
(Bayer 컬러 센서에서는 색 해상도가 절반이므로 하한을 15 ~ 20 px로 올려 잡는다. 3절 참조.)

**같은 검출 신뢰도에서 물리적 크기를 3 ~ 4배 작게 가져갈 수 있다.** 게다가 블롭 centroid는
수백 픽셀의 가중 평균이라, 코너 4점에서 나오는 태그 중심보다 노이즈에 강하다.

작은 마커를 원한다는 요구사항이 색 마커에 유리하게 작용한다.

## 3. 카메라 조건

### 스펙에서 나오는 수치

| 항목 | 값 |
|---|---|
| 해상도 | 2448 × 2048 |
| 센서 | Sony IMX250 **global shutter** CMOS |
| 픽셀 크기 | 3.45 µm |
| 센서 크기 | 8.45 mm × 7.07 mm |
| 프레임레이트 | 79.1 fps @ full |
| 픽셀 포맷 | **Bayer RG8 / Bayer RG10** (raw 만 출력) |
| 노출 | UltraShort 1 ~ 100 µs / Standard 20 µs ~ 1 s |
| 게인 | 0 ~ 24 dB, SNR 40.58 dB |
| 인터페이스 | USB 3.0 |
| 프로그래머블 제어 | image size, gain, exposure time, trigger/flash polarity |

**global shutter라는 점이 중요하다.** 빠르게 스윙하는 다리를 찍어도 rolling shutter 왜곡이
없다. 색 마커 추적에 유리한 출발점이다.

### Bayer 출력이라 자동 화이트밸런스가 없다

카메라가 **raw Bayer만 내보내고** 프로그래머블 제어 목록에 화이트밸런스가 없다. 디모자이크와
WB가 전부 호스트 쪽이므로, 고정 게인으로 처리하면 **자동 WB가 애초에 개입하지 않는다.**

일반 카메라에서 색 추적의 최대 위험 요소인 auto WB가 이 구성에서는 사라진다. 대신 확인할
것이 하나 생긴다: **VZ 백엔드의 디모자이크 경로가 고정 게인을 쓰는지**를 봐야 한다.
`vzcam-test`의 GenICam 노드 워커로 auto 계열 노드가 있는지도 함께 확인한다.

### 대역폭은 색이라고 더 들지 않는다

```
Bayer RG8 = 1 byte/px  ->  2448 × 2048 = 5.01 MB/frame
79.1 fps × 5.01 MB = 396 MB/s     <- USB 3.0 실효 한계에 이미 붙어 있다
```

Bayer는 gray와 같은 1 byte/px이므로 **버스 부담이 동일하다.** 색으로 바꾼다고 3배가 되지
않는다.

대신 **호스트에 디모자이크 비용이 새로 생긴다.** 5 MP를 79 fps로 처리하는 것은 프레임 예산
12.6 ms에 부담이다. 여기서도 **ROI가 답이다.** 다리 영역으로 크롭하면 디모자이크와 분류
비용이 같이 줄고, 뒤에 나오는 렌즈 왜곡도 함께 줄어든다.

**2×2 비닝은 피한다.** Bayer 센서에서 비닝은 색 채널을 섞을 위험이 있다. 해상도를 줄여야 하면
ROI로 자르는 것이 안전하다.

### Bayer 보간이 작은 마커에 영향을 준다

Bayer는 R과 B를 전체 픽셀의 25%에서만 샘플링한다. **작고 채도 높은 마커의 가장자리에 색
프린징**이 생기고, 실효 색 해상도가 휘도의 절반이다. 지름 20 px 마커면 실제 샘플된 R 픽셀이
100개 남짓이다.

그래서 **지름 하한을 15 ~ 20 px 아래로 내리지 않는다.** 아래 "정확도는 오히려 유리하다"에서
말한 10 px은 흑백 기준이고, Bayer 컬러에서는 여유를 둬야 한다.

디모자이크는 최속 bilinear 대신 edge-aware(`COLOR_BayerRG2BGR_EA`)를 쓰면 프린징이 줄어든다.
점수 가중 centroid가 프린징 픽셀에 낮은 가중을 주므로 실제 중심 오차는 크지 않을 것으로 본다.

### 마커 크기 계산

```
fx_px = f_mm / 0.00345
d_px  = fx_px · D_m / Z_m
```

렌즈 12 mm, 작업거리 3 m 기준 예시다.

```
fx = 12 / 0.00345 = 3478 px
시야 = 8.45/12 × 3000 = 2113 mm (가로), 7.07/12 × 3000 = 1768 mm (세로)

D = 17 mm  ->  d_px = 3478 × 0.017 / 3 = 19.7 px
D = 20 mm  ->  d_px = 23.2 px
D = 50 mm  ->  d_px = 58 px   (현재 AprilTag)
```

**17 ~ 20 mm 마커가 20 px 안팎으로 잡힌다.** 현재 태그가 50 mm이므로 약 1/3 크기다.

### 노출 시간 (반드시 조정 필요)

현재 `configs/vz-frontal.json`은 `"exposure_us": 8000`이다. 색 마커 추적에는 너무 길다.

```
이미지 상 속도 = fx · v / Z = 3478 × 3 / 3 = 3478 px/s   (발 스윙 v ≈ 3 m/s)

노출 8000 µs  ->  27.8 px 번짐
노출 2000 µs  ->   7.0 px
노출 1000 µs  ->   3.5 px
```

지름 20 px 마커가 8 ms 노출에서 20 × 48 짜리 줄무늬가 된다.

등속 운동의 모션 블러는 centroid를 보존하므로 위치 정확도 자체는 덜 상한다. 다만
**원형도 필터가 이 줄무늬를 탈락시킨다.** 원형도를 느슨하게 잡거나 예측 속도로 완화해야 한다.

프레임 간격이 12.6 ms (79 fps)이므로 노출을 1 ~ 2 ms로 줄여도 프레임레이트에는 여유가 있다.
줄어든 광량은 조명으로 벌충한다. **조명 통제가 여기서 결정적 레버가 된다.** 노출을 낮추면
모션 블러와 색 불안정이 동시에 잡힌다.

### 캘리브레이션 파일은 필요 없다

`sagittal_pose_estimator.hh`가 명시한다.

> The angles are therefore recoverable from 2D tag centers alone: **no tag->camera pose, no depth,
> no camera intrinsics.**

색 마커 모드는 같은 estimator에 같은 2D 중심점을 먹이므로 이 성질을 그대로 물려받는다.
미터 스케일도 블롭의 겉보기 지름과 실제 지름의 비로 구하므로 intrinsics가 들어가지 않고,
그 값은 표시 전용이라 각도에 영향이 없다.

(frontal은 다르다. 태그 pose를 풀어야 해서 intrinsics가 반드시 필요하고, VZ는 SDK가 주지
않으므로 체스보드 캘리브레이션 파일이 필요하다. `configs/vz-frontal.json`의 `calib/vz-0.yml`이
그 용도다.)

#### 다만 렌즈 왜곡은 각도에 실린다

같은 헤더에 TODO가 있다.

> TODO: lens distortion is not corrected. Undistort the tag centers before the angle math once
> tags sit near the image border or the lens gets wider.

각도 계산은 이미지 평면이 충실한 투영이라고 가정한다. 방사 왜곡은 마커 중심을 옮기고 그만큼
뼈 각도에 편향을 남긴다. 크기를 가늠하면 이렇다.

```
반대각선 r_max = √(1224² + 1024²) ≈ 1596 px
상대 왜곡은 대략 r² 에 비례

코너 왜곡 1% 렌즈, 마커가 중심에서 r = 700 px 지점
  -> 1% × (700/1596)² = 0.19%,  변위 ≈ 1.3 px

뼈 길이 L = 400 px, 뼈에 수직인 차분 변위 δ 일 때
  각도 오차 ≈ δ / L
  δ = 1 px -> 0.14°,   δ = 3 px -> 0.43°
```

각도가 rest 대비 차분이라 편향이 어느 정도 상쇄되지만, 다리가 화면을 가로질러 스윙하므로
완전히 상쇄되지는 않는다.

**캘리브레이션보다 싼 해법이 먼저다.**

1. **다리를 화면 중앙에 둔다.** 왜곡이 r²로 커지므로 중앙 영역에서는 사실상 서브픽셀이다.
   sensor source API의 ROI 선택으로 프레이밍하면 공짜다.
2. **저왜곡 렌즈를 고른다.** 머신비전용 low-distortion 렌즈는 왜곡 0.1% 미만이 흔하고,
   그러면 위 계산의 변위가 0.13 px로 떨어져 무시 가능해진다. 렌즈 선택 한 번으로 끝난다.
3. 그래도 부족하면 체스보드로 intrinsics를 잡아 각도 계산 전에 중심을 undistort한다.
   위 TODO가 그것이며, 왜곡 계수를 쓰려면 `fx/fy/cx/cy`도 함께 필요해 결국 전체
   캘리브레이션이 된다.

운용에는 캘리브레이션이 필요 없고, 정확도를 위해서라면 **렌즈 선택과 프레이밍이
캘리브레이션보다 먼저이자 더 효과적**이다.

### 게인으로 광량을 벌충하지 않는다

노출을 줄이면 광량이 준다. 이것을 게인(0 ~ 24 dB)으로 메우면 SNR 40.58 dB가 그만큼 깎이고,
노이즈는 색 분류 정확도를 직접 갉아먹는다. 조명으로 벌충하는 것이 맞다.

노출·게인은 `app_config`에 이미 있으므로 프로파일에 고정값으로 박아 둔다.

## 4. 마커 물리 설계

### 모양: 평면 원형 디스크

sagittal 한정이라는 제약이 여기서 이득이 된다.

카메라가 측면에 있고 하지 세그먼트는 시상면 안에서만 회전하므로, **회전축이 카메라 광축과
나란하다.** 세그먼트 측면에 붙인 디스크는 아무리 회전해도 카메라를 계속 정면으로 마주본다.
단축(foreshortening)이 없다.

```
      카메라 광축 (= 회전축)
           ●------------------>  [디스크]  회전해도 항상 원으로 보임
                                    ↺
```

frontal로 확장한다면 그때는 **반구(dome)**가 유리하다. 구의 투영은 방향과 무관하게 항상
원이라 겉보기 중심이 이동하지 않는다.

### 재질: 무광

광택 마커는 정반사 하이라이트가 생기고, 그 픽셀은 채도가 0으로 떨어져 색 정보가 통째로
사라진다. 블롭 한가운데 구멍이 뚫려 centroid가 편향된다.

### 테두리: 얇은 검정 링

마커 둘레에 1 ~ 2 mm 검정 링을 두면 배경과의 경계가 선명해지고, 디포커스나 블루밍으로
배경색이 마커 가장자리에 번지는 것을 막는다. 비용 대비 효과가 크다.

### 색 선택

피해야 할 색부터 정리한다.

| 색 | 문제 |
|---|---|
| 빨강 | 안전 표시, 피부 톤과 근접 |
| 노랑 | 조명 색온도에 따라 흰색과 붙음 |
| 초록 | 안전 표시, 비상구 |
| 파랑 | 청바지, 작업복 |

권장 순서는 **마젠타/핑크 → 형광 주황 → 시안**이다. 마젠타는 산업 환경에 거의 없고 채도가
높으며 검정 exo, 검정 벨트, 회색 벽 어디와도 겹치지 않는다.

### 색은 1개

sagittal은 근접 다리 하나만 마커를 붙이므로 마커가 4개(골반/무릎/발목/발)다. **네 개 모두 같은
색을 쓴다.**

hue 여러 개를 조명 변동 하에서 안정적으로 분리하는 것은 생각보다 어렵고, 색을 늘린다는 것은
곧 **시험소마다 현장에서 적합해야 할 모델이 하나 더 는다**는 뜻이다. 두 클래스의 Lab 구름이
겹치는 순간 그 검증 장치가 오히려 고장 원인이 된다.

대신 이 설비가 공짜로 주는 제약이 있다. 대상이 **1-DOF 힌지 강체 로봇**이고 트레드밀 위에서
카메라 거리도 고정이라, **마커 간 이미지 거리가 걷는 내내 거의 불변**이다. 색이 하려던 검증을
기하가 대신하고, 조명이 변해도 뼈 길이는 안 변하니 오탐도 없다(5절).

**클래스는 그래도 목록이다.** 현장에서 수직 순서 배정이 실제로 깨지면 색을 하나 늘리는 것이
config 편집과 샘플링 한 번으로 끝나야 한다. 그때 `joints_def` 테이블에 색 열을 더해 `A,B,A,B`로
가면 되고, 검출기는 손대지 않는다.

## 5. Identity 배정

AprilTag은 `id`를 공짜로 준다. 색 블롭은 안 준다. **이 설계에서 가장 큰 작업이 여기다.**

`color_marker_assigner`가 세 단계로 푼다.

```
1단계  초기 배정: y 오름차순 = 골반, 무릎, 발목, 발
       + 뼈 길이비 검증
2단계  이후 프레임: 예측 기반 최근접    직전 위치 ± 반경 R 안
복구   N 프레임 연속 불완전 배정 시 전체 프레임 재탐색 + 순서 재배정
```

2단계가 주는 이득이 크다. **배경에 붉은 물체가 있어도 예측 위치에서 멀면 아예 후보에서
탈락한다.** 오검출이 사실상 사라지고 연산량도 준다.

### 뼈 길이비 검증

강체라 골반-무릎, 무릎-발목, 발목-발의 이미지 거리가 고정이다. 배정이 한 칸 밀리면 "허벅지"
자리에 골반→발목이 들어와 거리가 두 배쯤 되므로 즉시 걸린다.

기준 거리는 **rest pose 를 보정하는 순간**에 잡는다. 그 순간이 조작자가 화면을 보며 배정이
맞는지 직접 확인하는 유일한 시점이라서다. lock 시점에 자동으로 잡으면 틀린 배정을 정답으로
박아 놓고 이후 맞는 배정을 계속 거부하게 된다.

기준을 그 프레임에서 뽑으므로 **카메라를 비스듬히 설치해 생긴 왜곡은 기준과 측정 양쪽에 똑같이
실려 상쇄된다.** 남는 것은 다리 자세에 따라 변하는 부분뿐이다.

| 설치 오차 | 자세 의존 단축 (θ=60°) | 원근 변동 | 합계 |
|---|---|---|---|
| 15° | 2.5% | 3.5% | 약 6% |
| 30° (눈에 띄게 비스듬) | 9.9% | 6.7% | 약 17% |

한 칸 밀림은 0.5배나 2.0배로 나타나므로, 기본 밴드 `[0.65, 1.35]` 사이에 여유가 있다. 육안으로도
비스듬한 설치라면 `bone_length_tolerance` 를 0.45 정도로 올린다.

**`enable_bone_length_check` 로 끌 수 있다.** 강체 가정이 안 맞는 설치에서는 이 검사가 정상
배정을 계속 거부하므로, 원인이 길이비인지 순서/반경인지 가르는 첫 조작이 이 스위치다.

## 6. 분류 알고리즘 계층

### Layer 0 — 카메라 고정

알고리즘이 아니지만 효과가 가장 크다. 3절 참조.

### Layer 1 — 색공간과 거리 함수

HSV 축정렬 박스를 쓰지 않는다. 실제 픽셀 구름은 기울어진 타원인데 박스는 그것을 담지 못한다.

**CIE Lab의 (a\*, b\*) 평면에서 마할라노비스 거리**를 쓴다.

```
Lab 변환 -> (a, b) 만 사용 (L = 밝기는 버림)
d² = (p − μ)ᵀ Σ⁻¹ (p − μ)
마스크 = d < threshold
```

얻는 것이 셋이다.

- L을 버리므로 **그림자에 강해진다**
- 공분산이 실제 분포를 담아 오검출이 줄어든다
- **노브가 6개(H/S/V min-max)에서 1개(임계 거리)로 줄어든다.** 튜닝 관점에서 결정적이다

`cvtColor(BGR2Lab)` 한 번이면 되고 이후는 룩업 테이블로 충분히 빠르다.

#### 밝기 불변은 근사다

a\*, b\* 를 구하는 식에 세제곱근이 들어 있다.

```
a* = 500 · ( f(X/Xn) − f(Y/Yn) ),   f(t) ≈ t^(1/3)
```

밝기가 k배가 되면 X, Y, Z 가 함께 k배가 되고, **a\*, b\* 가 k^(1/3) 배로 이동한다.**

| 노출 변화 | a\*, b\* 배율 | `mean_a = +62` 이었다면 |
|---|---|---|
| 2배 | 1.26 | +78 |
| 절반 | 0.79 | +49 |

표준편차가 3~5 인 모델에서 이건 몇 표준편차 밖이다. 그늘처럼 폭이 작은 변동은 공분산이
흡수하지만 **노출이나 게인을 바꾸는 것은 다른 색으로 바꾸는 것과 같다.** 그래서 색 모델은
자기가 측정된 노출·게인을 함께 들고 다니고, 앱이 카메라를 그와 다르게 열 때 경고한다(8절).

근본 해법은 스케일 불변인 특징 공간이다. 정규화 rgb `(R/(R+G+B), G/(R+G+B))` 는 k배에 **정확히**
불변이라 같은 마할라노비스를 그대로 쓸 수 있다. 다만 (a, b) 가 정수 256×256 이라 성립하던 룩업
테이블 한 장이 사라지고 픽셀당 나눗셈이 붙는다. 현장에서 노출 관리가 반복적으로 실패한다면
그때 저울질할 항목이다.

### Layer 2 — 조명 드리프트 보정

시야 안 고정 위치에 **회색 기준 패치**를 붙이고, 매 프레임 그 평균값으로 채널 게인을 계산해
분류 전에 적용한다 (von Kries 적응).

```
gain_c = target_c / measured_c        (c = R, G, B)
```

ROI 하나 지정하는 것이 전부인데, **조명 색온도가 서서히 변해도 색 모델이 유지된다.** 형광등
예열, 계절, 창문 유입광 같은 것을 흡수해서 시험소마다 재튜닝하는 빈도를 크게 줄인다.

### Layer 3 — 마스크 정제

```
open(3×3)    스펙클 제거
close(5×5)   하이라이트 구멍 메움
connectedComponentsWithStats
필터: 면적 [min,max] / 원형도 4πA/P² / 채움율 A/bbox / 종횡비
```

**각 필터의 탈락 사유를 카운트해 GUI에 노출한다.** "왜 안 잡히는지"를 즉답할 수 있느냐가
현장 튜닝 속도를 결정한다.

모션 블러 때문에 원형도 필터는 느슨하게 잡거나 예측 속도에 따라 완화한다.

### Layer 4 — 서브픽셀 중심

이진 centroid 대신 **점수 가중 centroid**를 쓴다.

```
w(p)   = max(0, 1 − d(p)/threshold)
center = Σ w·p / Σ w
```

경계 픽셀이 부분 가중되어 표준편차가 눈에 띄게 줄어든다. 구멍을 메운 컨투어 내부에서
계산한다.

### Layer 5 — 시간 게이팅

5절의 identity 3단계와 통합해 **예측 ROI 안에서만 탐색**한다. 전체 프레임 탐색은 lost
상태에서만 수행한다.

### Layer 6 — 기존 파이프라인 재사용

One Euro 스무딩, 홀드, `reset_gap`은 `sagittal_pose_estimator`에 이미 있다. 검출기는 원시
중심만 내고 나머지는 그대로 태운다.

## 7. 아키텍처

### 이음매가 이미 준비되어 있다

`pose_estimator_base.hh`가 이 전환을 예상하고 쓰여 있다.

> What one frame's measurement looks like depends on the viewing plane and on the marker
> technology (tag ids and corners, **a blob centroid**, ...), so each implementation declares its
> own `update()` taking the input it needs.

`sagittal_pose_estimator`가 검출에서 실제로 쓰는 것은 셋뿐이다.

```cpp
tag_id_to_joint_id(det.id)   // 관절 매핑
det.center                    // 2D 점
mean_edge_px(det.corners)     // 미터 스케일 (표시 전용)
```

그리고 헤더가 명시한다: *"the angles this estimator produces do not depend on it
[`tag_size_m`]"*.

**즉 각도 정확도는 마커 크기 추정과 무관하다.** 블롭 지름이 흐릿해도 각도는 영향받지 않는다.
위험이 크게 줄어드는 지점이다.

### 새 관측 타입

`tag_detection_t`를 재사용하지 않는다. `hamming`, `decision_margin`, `pose_candidates`가
블롭에는 의미가 없어 죽은 필드가 된다.

```cpp
// src/pose/joint_measurement.hh
struct joint_2d_measurement_t {
    joint_id_t joint_id;                    // 이미 이름이 붙어서 온다
    Eigen::Vector2d center_px;              // 서브픽셀 중심
    std::optional<double> meters_per_pixel; // 이 측정이 제공하는 미터 스케일
};
```

두 추정기 모두 이 씸으로 입력을 받는다(3D 추정기는 `joint_3d_measurement_t`). 검출 결과를 관절
이름까지 끌고 가는 일은 **`pose::marker_tracker_base`** 가 맡는다. 마커 기술마다 다른 것 전부가
그 인터페이스 뒤에 있다.

| 무엇 | 태그 | 색 마커 |
|---|---|---|
| 필요한 프레임 | gray8 | bgr8 |
| 관절 이름 붙이기 | `id` 표 조회 | `color_marker_assigner` |
| rest pose 보정 때 | 없음 | 뼈 길이 기준 latch |
| 스트림 점프 때 | 없음 | 배정기 |

`pose_estimator_base`가 `update()`를 기반 클래스에서 뺀 이유가 정확히 이것이므로 이 코드베이스의
관용에 맞는다.

### 파이프라인 배선

`exo_pose_pipeline`에 `_select_estimator()`와 같은 모양으로 `_select_detector()`를 두고
config의 `detector.kind`로 분기한다. **기존 태그 경로는 손대지 않는다.**

관절과 마커의 매핑은 `joints_def.hh` 테이블에 그대로 둔다. `tag_id` 옆에 색 클래스 열을
하나 추가하면 "관절 추가 = 테이블 한 줄" 성질이 유지된다.

```
데이터 흐름 (변경 없음)
백엔드 → provider → observer → [검출기] → sagittal estimator → GUI / 서버 broadcast
                                   ↑
                        여기만 config 스위치로 교체
```

### 검출기는 백엔드를 모른다

검출기는 `cv::Mat` 하나를 받는다. 어느 백엔드가 만든 프레임인지 알지 못하고 알 필요도 없다.
따라서 **색 마커 모드를 특정 카메라 전용으로 제한하지 않는다.** 제한을 걸려면 지금 없는 검사를
새로 넣어야 하므로 오히려 코드가 늘고, 백엔드를 아는 seam을 provider로 한정한 계층 원칙도
깨진다. 무엇보다 **녹화 재생이 막혀** 오프라인 튜닝 흐름이 사라진다.

색 재현이 카메라마다 다른 것은 사실이지만, 색 모델은 config 프로파일 안에 있고 프로파일은
설치별이다. **VZ 프로파일 하나만 내보내면 그것이 곧 "VZ에서 검증된 설정"**이고, 다른 카메라를
쓰려는 쪽은 자기 프로파일을 만들면 된다. 코드 변경도 검증 부담도 없다.

정당한 검사는 백엔드가 아니라 프레임 포맷이다. 흑백 소스가 들어오면 명확한 에러로 거절한다.

### bring-up 하네스: `tools/vzcam-test`

검출기를 프로덕션에 꽂기 전에 `vzcam-test`에서 먼저 돌린다. 설치용 색 캘리브레이션은 9절대로
디버거가 재므로, 이 하네스에서 적합한 모델은 어디에도 저장되지 않는다. 여기서 하는 일은 이
카메라에서 알고리즘이 도는지, 조명과 노출이 쓸 만한지를 GenICam 노드를 직접 만지며 보는 것이다.
이미 갖춘 것이 그대로 필요한
것들이다.

- GUI 셸 재사용 (`app_base` / `app_renderer_sdl3` / `frame_texture` / `log_console`)
- VZ 스트리밍 + 실시간 어노테이트 오버레이, 검출 fps/ms 계측
- **GenICam 노드 워커** + 노출·게인·ROI·프레임 포맷 컨트롤
- config 프로파일이 없어 슬라이더로 즉시 반복 가능

**검출기 코드는 처음부터 `src/pose/`에 두고 `vzcam-test`가 링크한다.** 이미
`src/pose/tag_detector.{hh,cc}`를 그렇게 쓰고 있다. 이러면 포팅 단계가 아예 없어지고, 프로토타입과
프로덕션 구현이 갈라지는 일도 생기지 않는다.

```cmake
add_executable(${VZCAM_TEST_NAME}
    ...
    "src/pose/tag_detector.hh"
    "src/pose/tag_detector.cc"
    "src/pose/color_marker_detector.hh"   # 추가
    "src/pose/color_marker_detector.cc"
)
```

한 가지 손볼 곳이 있다. `vzcam_test_app.cc`의 태그 검출 토글이 카메라를 gray 출력으로 바꾼다
(*"One channel is enough, so enabling detection puts the camera in gray output."*). 색 마커는
컬러 프레임이 필요하므로 검출 모드에 따라 포맷을 나눈다. 포맷 전환 기능 자체는 이미 있다.

## 8. 튜닝 파라미터

기존 config 철학(설치 config는 JSON 하나, 프로파일별)에 그대로 얹힌다.

```json
"detector": {
  "kind": "color_marker",
  "apriltag": { "...": "태그 경로도 그대로 남아 있어 전환해도 튜닝을 잃지 않는다" },
  "color_marker": {
    "calibration": {
      "detector": {
        "model": {
          "mean_ab": [62.4000, -18.1000],
          "cov_ab": [[9.2000, 1.4000], [1.4000, 7.8000]],
          "max_distance": 3.0000
        },
        "min_area_px": 60.0, "max_area_px": 6000.0,
        "min_fill": 0.55, "max_aspect": 3.0, "min_score": 0.15,
        "open_kernel_px": 3, "close_kernel_px": 5
      },
      "frame_resolution": [2448, 2048]
    },
    "assigner": {
      "leg": "left",
      "marker_diameter_m": 0.018,
      "search_radius_px": 60.0,
      "enable_bone_length_check": true,
      "bone_length_tolerance": 0.35,
      "lost_frames_before_full_search": 10
    }
  }
}
```

`assigner` 블록은 `color_marker_assigner::options_t` 를 그대로 비춘다. `frontal` / `sagittal` 이
추정기 옵션을 비추는 것과 같은 형태라, 파라미터를 하나 더하면 그 구조체 안
`DECLARE_SERIALIZABLE_FIELDS` 목록의 한 줄이 전부다. 각 타입이 자기 키 목록을 멤버 옆에 들고
있어서(`utils/serializable.hh`), 필드와 키가 한 자리에서 같이 늘어난다.

핵심은 다음과 같다.

**파일은 하나다.** 색을 재는 도구가 프로파일을 읽고 쓰는 그 앱이라, 캘리브레이션을 옆 파일로
뺄 이유가 없다. 뺐다면 소스 주소와 노출·게인을 양쪽에 적어 두고 열 때마다 대조해야 하는데,
한 파일이면 `camera` 블록 바로 아래에 색이 있으니 어긋날 두 벌이 생기지 않는다.

**`calibration` 은 통째로 없을 수 있다.** 아직 아무도 안 잰 설치가 그 상태이고, 그때 검출기는
기본값으로 돌아 아무것도 내지 않는다. 블록 안 개별 필드를 null 로 두는 대신 블록 하나를 통째로
비우므로, 숫자 옆에 "이건 유효하지 않다" 를 적을 자리가 생기지 않는다.

**`frame_resolution` 만 측정 조건으로 남는다.** 소스 주소도 노출도 게인도 바로 위 `camera`
블록에 있어 복사가 되지만, 카메라가 실제로 내주는 프레임 크기는 거기 없다. ROI 나 비닝이나 다른
센서가 마커의 픽셀 수를 바꾸고 블롭 문턱은 픽셀로 적혀 있으므로, 소스를 열 때 이 값과 대조해서
다르면 경고한다.

**블롭 필터가 색과 같은 블록에 있다.** 저 일곱 개는 전부 마커가 이 거리와 이 프레임 크기에서
픽셀 몇 개를 덮는가, 광택이 어떻게 반사되는가, 스윙이 얼마나 번지게 하는가로 정해진다. 색을
재는 그 자리에서 같이 정해지는 값이다. `min_score` 는 한 걸음 더 나아가 **모델 자체를 기준으로
매긴 점수**에 대한 문턱이라, 모델이 바뀌면 같은 숫자가 다른 뜻이 된다. 그래서 둘을 갈라 놓으면
한쪽만 갱신되는 순간 설명할 수 없는 검출 실패가 남는다.

**색 모델은 사람이 타이핑하지 않는다.** 디버거에서 이 설치의 프로파일을 열고 마커를 클릭해
샘플링한 뒤 Fit, 그리고 Config > Save Config As 를 누른다. 시험소별 절차가 그 세 걸음이다.

**노출·게인은 색 모드에서 값이 필수다.** 자동으로 두면 카메라가 운용 중에 밝기를 바꾸고, 고정된
모델이 그것을 따라갈 수 없다. `validate()` 가 `pose.detector.kind` 가 `color_marker` 인데
둘 중 하나라도 비어 있으면 설정 파일 에러로 거부한다.

**단 이 검사는 이 프로파일이 카메라를 열 때만 건다.** `camera.source` 가 녹화 파일이면 프로그램할
카메라가 없고 운용 중에 밝기가 변할 일도 없어서, 녹화로 색을 맞춘 프로파일은 노출·게인이 비어
있어도 열린다. 소스를 아예 안 적은 프로파일도 로드 시점에 아무것도 프로그램하지 않으므로 같다.

**카메라의 색 처리는 백엔드가 이름으로 고정한다.** 화이트밸런스, 감마, 채도, 휘도 LUT,
digital shift 는 전원을 꺼도 카메라에 남는 값이라 누가 언제 만졌는지에 따라 색이 달라진다.
`vz_frame_source::open()` 이 이들을 **카메라가 스스로 이름 붙인 상태**로 눌러 둔다.

| 노드 | 고정값 | 왜 |
|---|---|---|
| `BalanceWhiteAuto` | `Off` | 프레임마다 채널 비율을 다시 쓴다. 고정된 모델이 못 따라간다 |
| `LightSourcePreset` | `Daylight6500K` | 세 채널 비율을 이 프리셋이 정한다 |
| `GammaEnable` | `false` | 밝기에 따라 채널마다 다르게 휘어 마커를 안 옮기고도 a\*b\* 를 옮긴다 |
| `SaturationMode` | `Off` | 채도를 직접 곱한다. 모델이 재는 값에 가장 직접 작용하는 노브 |
| `LUTEnable` / `DigitalShift` | `false` / `0` | 같은 일을 다른 경로로 한다 |
| `ReverseX` / `ReverseY` | `false` | 색이 아니라 순서 문제다. 상하가 뒤집히면 배정의 y 순서 가정이 깨진다 |

**비율을 숫자로 직접 쓰지 않는 것이 핵심이다.** Bayer 센서는 초록에 훨씬 세게 반응하므로 세
비율을 1.0 으로 평평하게 만들면 화면이 초록으로 치우친다. 방을 닮은 화면을 만드는 비율은 벤더가
말할 값이고, 프리셋 이름이 그 값을 부르는 방법이다.

`BlackLevel` 만 고정하지 않는다. 디지털화 전에 더해지는 오프셋이라 올리면 a\*b\* 가 중성축으로
눌리지만(세제곱근이 오목해서 차이가 줄어든다), 카메라가 중립이라 부르는 값을 내놓지 않는다.
여기서 값을 지어내면 같은 카메라를 보는 다른 도구와 화면이 달라지므로, 대신 open 로그에 현재
값을 채널 비율과 함께 찍는다. 누가 바꿔 놓았다면 모델을 읽는 로그 바로 옆에서 보인다.

같은 이유로 센서가 흑백 포맷으로 남아 있는데 색 프로파일로 열면 open 이 실패한다. 흑백을
3채널로 늘리면 모든 픽셀이 무채색이라 아무것도 검출되지 않으면서 원인이 화면에 뜨지 않는다.

**`valid` 는 파일에 없다.** 파싱에 성공하고 공분산이 면적을 갖는 타원이면 그게 곧 적합된
모델이다. 파일 안에 "이건 유효하지 않다" 고 적을 수 있게 두면 바로 옆의 숫자와 모순될 수 있다.

**어느 다리인지는 `leg` 가 정한다.** 태그는 id 가 알려주지만 색은 못 한다. 여기가 그 자리다.

## 9. GUI 디버거

색 캘리브레이션은 **디버거에서 한다.** 디버거는 이 설치의 프로파일로 카메라를 열어 두고 있으므로,
적합할 때의 노출·게인·프레임 크기가 곧 운용할 값이다. 별도 도구에서 재고 옮겨 적으면 그 둘이
어긋날 수 있는데, 여기서는 어긋날 자리가 없다.

Control 패널의 `Color Model` 절이 지금 무엇이 설치돼 있는지 보여주고, 재는 것은 그 절의
`Sample...` 이 여는 카메라 창에서 한다. 프레임과 그것을 재는 컨트롤이 한 창에 있어서 마커를
크게 띄워 놓고 조준할 수 있다.

```
Control 패널                카메라 창
--------------------        ----------------------------------------------
model  a*+62.4 b*-18.1      Backdrop [camera|mask|score]  Radius 6  Max d 3.00
       sd 3.0/2.8  d<3.0    samples 4820 (need 100)  [Fit model] [Clear samples]
[ Sample... ]               +--------------------------------------------+
                            |            (카메라 프레임)                  |
                            +--------------------------------------------+
```

절차는 세 걸음이다. **창의 프레임 위에서 마커를 드래그해 훑고**, **Fit** 을 눌러 그 자리에서
검출이 어떻게 달라지는지 보고, 컨트롤 패널의 **Save Config As** 로 프로파일에 쓴다. Fit 은
돌고 있는 검출기에 모델을 바로 설치하므로 다음 프레임부터 결과가 바뀐다.

**저장 버튼은 하나다.** 색 모델도 블롭 필터도 관절 배정도 전부 프로파일에 들어가므로,
이 패널에는 저장이 없고 다른 컨트롤과 똑같이 `Save Config As` 가 가져간다. 저장할 때
`frame_resolution` 은 지금 열려 있는 소스가 내주는 크기로 채워진다.

**샘플은 스윙 전 구간에서 모은다.** 한 자세에서만 뽑으면 실제로 마커가 지나는 밝기 범위가
공분산에 안 담긴다. 그늘진 쪽까지 훑어야 한다.

**표본은 픽셀을 들고 있지 않는다.** `color_sampler` 는 합 다섯 개와 개수만 누적하므로, 몇 만
픽셀을 모아도 메모리가 늘지 않는다.

**Backdrop 이 "왜 안 잡히는가" 에 답한다.** `mask` 는 분류기가 통과시킨 픽셀, `membership score` 는
얼마나 확신하는지다. 마커가 검게 나오면 모델이 안 맞는 것이고, 배경이 하얗게 나오면 `Max distance`
가 넓은 것이다. 둘 다 프레임 한 장 분량을 매 프레임 복사하므로 **보고 있을 때만 생산한다.**

### 아직 없는 것

**1. a\*b\* 산점도 + 모델 타원**
현재 프레임 픽셀을 (a, b) 평면에 뿌리고 모델 타원을 겹쳐 그린다. **배경색 덩어리가 타원에
얼마나 가까운지 한눈에 보인다.** `color_sampler::points()` 가 표시용 표본점을 이미 모아 두고 있고,
읽는 곳이 이것뿐이다.

**2. 기준 패치 게인 추이 그래프**
조명 드리프트를 눈으로 확인. 6절의 보정을 붙일지 판단하는 근거가 된다.

자동 노출·화이트밸런스 경고 배너는 필요 없어졌다. 노출·게인이 auto 면 설정 파일이 거부되고,
화이트밸런스와 블랙레벨은 백엔드가 눌러 둔다(8절).

### 이미 있는 것을 활용한다

**녹화(mcap)와 재생이 이미 있다.** 이것이 튜닝 사이클을 결정적으로 바꾼다.

```
시험소에서 한 번 녹화 → 사무실에서 그 녹화로 파라미터 반복 조정 → 프로파일 저장 → 현장 적용
```

현장에 붙어 슬라이더를 만지는 대신 오프라인에서 돌릴 수 있다. 포즈 트레이스 덤프에도 블롭
원시 데이터를 실어 두면 프레임 단위 재현 검증까지 된다.

외부 기준 장비 없이 정량 검증할 수 있는 방법이 있다.

**같은 관절에 AprilTag과 색 마커를 나란히 붙이고 두 검출기를 동시에 돌려** 중심 좌표를

검출기 추상화를 만들어 두면 config 스위치로 A/B가 되므로 추가 비용이 거의 없다.

## 11. 단계 계획

| 단계 | 내용 | 위치 | 상태 |
|---|---|---|---|
| 1 | 마커 시트 생성 툴 (PDF, mm 정확, 검정 링, 색 패치, 자 눈금) | `tools/marker-sheet/` | 완료 |
| 2 | GenICam 노드 확인(auto 계열), 노출 1 ~ 2 ms + 조명 세팅 | `vzcam-test` (기존 기능) | 현장 |
| 3 | 색 클래스 1개짜리 수직 관통: 클릭 샘플링 → a\*b\* 모델 → LUT 마스크 → 블롭 → centroid, 오버레이, 컬러 포맷 분기 | `src/pose/`, `vzcam-test` 링크 | 완료 |
| 4 | 마커 색·지름 실측 확정, 짧게 녹화 | `vzcam-test` | 현장 |
| 5 | 측정 씸(`joint_2d/3d_measurement_t`) + `marker_tracker_base` 추상화 + identity 배정 | `src/pose/` | 완료 |
| 6 | `detector.kind` config 스키마 + 파이프라인 배선 + GUI 컨트롤 | `src/` | 완료 |
| 7 | 프로파일 내 색 캘리브레이션 + 디버거 샘플링·적합·저장, 카메라 응답 고정 | `src/`, `src/hw/` | 완료 |
| 8 | 기준 패치 조명 보정 | `src/pose/` | 보류 |
| 9 | 현장 녹화 → 오프라인 튜닝 → 프로파일 확정 | 현장 | 시험소당 반나절 |

3단계까지가 "먼저 눈으로 확인한다"에 해당하고, 5단계부터가 프로덕션 경로다.

### 보류한 것

| 항목 | 왜 미뤘나 |
|---|---|
| 기준 패치 조명 보정 (von Kries) | 실제 조명 드리프트를 측정한 뒤에 붙이는 것이 맞다 |
| 색 다중 클래스 | 4절 참조. 강체 기하가 대신하고 있어, 순서 배정이 실제로 깨진 다음에 넣는다 |
| a\*b\* 산점도 + 모델 타원 | ImPlot 히트맵 + 타원. `color_sampler::points()` 가 이미 표본점을 모으고 있어 그리기만 남았다 |
| 트레이스에 블롭 원시 데이터 | 프레임 단위 재현 검증용 |

2단계(조명·노출)를 3단계보다 앞에 둔 이유가 있다. **모션 블러가 27 px씩 나는 상태로 검출기를
튜닝하면 잘못된 파라미터로 수렴한다.**

### 3단계에서 간이 임계화를 거치지 않는 이유

HSV 축정렬 임계화를 먼저 만들었다가 나중에 교체하는 순서를 택하지 않는다.

**분류기가 무겁지 않다.** 샘플링과 2×2 공분산 적합, 마할라노비스 판정을 합쳐 40줄 남짓이고
Eigen은 이미 의존성에 있다. 간이 버전과 며칠 차이 나는 작업이 아니다.

**오히려 더 빠르다.** OpenCV의 `CV_8U` Lab은 a, b가 각각 0 ~ 255이므로 **256×256 룩업
테이블(64 KB) 하나가 분류기 전체를 담는다.** 픽셀당 조회 1회로, `inRange`의 비교 6회보다
싸다. 5 MP를 79 fps로 처리해야 하는 상황에서 무시할 수 없는 차이다.

**간이 버전으로 물리 결정을 내리면 위험하다.** 축정렬 박스로 "이 색은 분리가 안 된다"고
판단한 색이 마할라노비스로는 충분히 분리되는 경우가 생긴다. 마커 색과 지름은 되돌리기
비싼 결정이므로 최종 분류기로 판단해야 한다.

**부트스트랩 문제도 없다.** 샘플링에는 분류기가 필요 없다. 라이브 컬러 영상에서 클릭한 지점의
픽셀을 모으면 되고, `a*b*` 산점도는 분류를 하기 전에 이미 배경과 마커의 분리도를 보여준다.

미루는 것은 알고리즘 품질이 아니라 범위다. 3단계에서 빼는 것은 identity 배정, 조명 보정,
시간 게이팅, config 배선이며 **이들은 진짜로 복잡하거나 선행 조건이 있다.** 색 클래스를 하나로
두면 배정 문제 자체가 생기지 않고, 마커 하나를 손에 들고 흔들어 보는 것만으로 색·지름·노출·조명
결정이 전부 난다. 3단계에서 쓴 코드는 전부 최종본에 남는다.

## 12. 정리

걱정하기 쉬운 색 임계화는 사실 가장 쉬운 부분이고, 진짜 작업은 **identity 배정**과 **샘플링
기반 튜닝 워크플로**다.

조명을 통제할 수 있다는 것은 소극적 위안이 아니라 **노출을 1 ~ 2 ms로 내려 모션 블러와 색
불안정을 동시에 잡는 레버**다. 조명 설계를 먼저 하는 것이 순서상 맞다.

sagittal 한정이라는 제약도 이득이다.

- 회전축이 카메라 광축과 나란해서 평면 디스크로 충분하다
- 다리 하나만 추적하면 된다
- 각도가 미터 스케일과 무관하다
- **카메라 캘리브레이션이 필요 없다** (남는 것은 렌즈 왜곡뿐이고, 렌즈 선택과 프레이밍으로 해결)
- 카메라가 global shutter라 rolling shutter 왜곡이 없다
